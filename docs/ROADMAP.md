# VRCX-K 开发路线图（概览）

> **本文件 = 里程碑级概览**（落 M 阶段粒度）。开发阶段的**任务级细化**在 GitHub issue 逐层派生（总览 → M 总览 → subissue），不在本文件锁死。
> 下文「功能线 BP 拆分表」是**预演**（方向参考），到对应开发阶段再细化定稿；基建里程碑对齐架构 §4.1，功能分层对齐 §4.7。

## 0. 项目目标（双线）

- **平台**：Cordis + Tauri + React，社区插件生态（架构 v4.2 定稿）。
- **产品（主线）**：把 VRCX 能力**完整复刻**为官方维护的 **base 插件包**——内含多个子插件（登录/WS、数据库引擎、好友列表、位置变更、通知、照片…），跑在 Cordis 宿主上。
- **双线关系**：基建线（宿主/壳/插件机制，M0-M5）铺路；功能线（base 包 BP）逐块搬入成为 Cordis 插件。功能线是用户可见主线，基建线是支撑。
- **终态**：base 包稳定后开放社区市场，垂直功能由社区插件承接（架构 §4.7 第三档）。

## 3. 功能线预演：base 插件包 BP 拆分表

> ⚠ **预演**：下表给出 VRCX 能力域 → base 子插件 的拆分方向（据 VRCX 官方功能清单 vrcx-team/VRCX README），**非承诺**。每 BP 开发时在 issue 细化任务/验收/依赖，拆分可能随架构演进调整。

| BP | base 子插件 | 复刻能力 | 依赖 | 预计接入 |
|---|---|---|---|---|
| BP-0 | 核心骨架（base 容器） | 子插件装配规范、服务契约、统一 ctx 命名 | M2 | M2 起 |
| BP-1 | 登录与 WS 模块 | VRChat 登录(含 2FA)、WebSocket 长连、Auth/Cookie | M1 壳跑通即动工 | M2/M3 |
| BP-2 | 数据引擎/驱动 | SQLite 持久化、schema 迁移、好友/历史/收藏/照片索引 | 驱动选型 | M2 |
| BP-3 | 好友/世界/Avatar 管理 | 三表管理、在线/位置/Avatar 追踪、好友度历史、备注 | BP-1/2 | M2/M3 |
| BP-4 | Feed/GameLog 事件 | 活动流、GameLog 解析、事件过滤 | BP-1 | M2/M3 |
| BP-5 | 通知系统 | 收/发邀请、好友请求、实例信息、桌面通知(经双手) | BP-3 + 壳 | M3/M4 |
| BP-6 | 照片与媒体 | 游戏截图存世界数据、照片库、avatar/world 图上传 | BP-2 | M4 |
| BP-7 | 当前实例 stats | 实例玩家/统计、视频链接日志 | BP-1/4 | M3 |
| BP-8 | 社交状态预设 | 状态+描述预设快捷应用 | BP-1 | M3 |
| BP-9 | 服务器状态监控 | VRChat 服务器健康指示 | BP-1 | M3 |
| BP-10 | Discord Rich Presence | 实例详情→Discord（平台桥，可选） | BP-1 | M4+ |
| BP-11 | VR Overlay | 事件实时 VR Overlay（重能力） | M4（C 类 runner） | M4 |
| BP-12 | 自动启动/崩溃恢复 | 启动 VRC 时拉起配套、崩溃自动回实例 | 壳/进程 | M4 |
| BP-13 | 导出/导入 | 好友/Avatar/笔记导出、收藏组导入 | BP-2 | M4 |
| BP-14 | 搜索 | 全局搜索(用户/世界/Avatar/组)、快速模糊搜索 | BP-2 + 前端 | M3/M4 |
| BP-15 | Dashboard widgets | 可定制多面板布局(Feed/GameLog/Instance) | M3 前端契约 | M4 |
| BP-16 | Activity Heatmap | 在线活跃热图 | BP-2 + 前端 | M4+ |

**预演分档**（对齐架构 §4.7）：
- **首版（v1.0）**：BP-0/1/2/3/4/5/7/8/9 + 基础 UI（登录页/好友/世界信息三栏）→ M2-M3 产出。
- **后续（v1.x）**：BP-6/12/13/14/15/16 + 系统通知、收藏/历史 → M3-M4 产出。
- **交社区**：BP-10/11（重能力、平台桥）随 M4 市场开放后生态化。

## 4. 协作约定

- **概览 ↔ 细化的分工**：本文件只回答「现在到哪个 M、base 包往哪个方向」；「这个 M 具体做哪几个任务、验收什么」在 GitHub M 总览 issue，开工即细化并派生 subissue。
- **每阶段开工动作**：新建 M 总览 issue → 拆任务 subissue（含验收/依赖）→ 实现 → 勾选回填（GitHub task list 引用）。
- **保持预演**：BP 拆分与交付档位是方向，进开发阶段按当时架构/生态重估，不教条。
- **风险/上游**：架构 §4.2 风险 + §4.5 上游追踪（bun#35690 等），每里程碑复核。
